# 论文简介与中文解读维护规范

记录日期：2026-10-16。本文记录本次四篇工作介绍的已确认要求，供以后新增研究和修改现有页面时沿用。用户后续提出的新要求优先；本规范可随实际使用继续修订。

## 1. 每项研究交付两层内容

| 内容 | 读者需要得到什么 | 位置 |
| --- | --- | --- |
| 首页简介 | 快速理解研究问题、主要贡献和有依据的优势，决定是否继续阅读 | `_pages/includes/pub.md` |
| 独立中文解读 | 理解为什么做、为什么这样设计、相较已有方案改进在哪里、实验证明了什么 | `_pages/research/<slug>.md`，对应 `/research/<slug>/` |

默认读者懂技术，但未必研究该论文的具体方向。中文解读采用作者讲解自己工作的语气，可以用“我们”，但不能补写没有材料支持的研究经历、选题故事或试错过程。

验收时，读者应当能在读完开头后说清“为什么值得做”，读完正文后说清“你们改进了什么、证据是什么”。完整体现意义，指覆盖核心问题、贡献和证据，不要求搬运论文全部细节。没有真实读者反馈时，不宣称某种写法是最优或读者一定喜欢。

## 2. 首页简介：价值优先，一段写清

每篇正式论文标题下面放一段中文简介，通常约 120–180 个汉字，可按内容稍作调整，不设机械字数上限。顺序优先为：

1. 面向什么对象、存在什么具体问题。
2. 本工作提出了什么关键思路，设计有什么特点。
3. 最有代表性的结果或相较对比方案的优势，并保留必要实验条件。

控制术语密度。首页通常无需连续列出算法名、模块名和完整指标体系；陌生指标没有解释时，优先说明它代表的实际效果。详细的参数、消融和局限放进独立解读。

若比较结果必须依赖特定协议，在句中用“在主实验中”“在所报告的设置下”等限定。不要把某次测试中全部通过写成任意条件下都可靠，也不要将用于校准的正常数据要求扩展成整个训练过程无需攻击样本。

条目排列沿用已确认的形式：正式英文标题 → 分区/检索等标签 → 中文简介 → 会议/期刊与作者 → 中文解读和 PDF 链接。正式英文标题用列表内的 Markdown 三级标题（`- ### 论文标题`）单独成行，字号与字重高于简介；标签放在标题下一段，避免抢占标题的首行空间。标题样式由 `assets/css/academic.css` 统一维护，覆盖桌面与手机端；原有标题链接保留。作者本人加粗。已有分区、检索和会议标签沿用用户确认信息；更新这些信息时单独核实，不凭记忆补写。

在 Markdown 列表中，简介、作者信息和链接段落使用四个空格缩进，保证它们仍属于同一个论文条目。例如：

```markdown
- ### Formal English Paper Title

    ``已有标签``

    一段中文简介，写清问题、思路、贡献与代表性证据。

    ``会议或期刊 年份`` · **Renchao Li**, Other Authors

    <a href="{{ '/research/example/' | relative_url }}" target="_self">中文解读 →</a> · [PDF]({{ '/assets/pdf/example.pdf' | relative_url }})
```

## 3. 独立解读：解释设计选择，贡献融入叙事

开头用两三段集中说明实际约束、核心思路与代表性结果。让价值尽早出现，避免长篇领域背景后才介绍本工作。

正文按论文特点组织，一般覆盖以下问题，但不要求每篇使用相同标题或相同章节数：

- 已有方案在什么条件下受到限制，为什么需要这项研究。
- 关键设计改变了什么，为什么适合研究对象与约束。
- 方法如何工作，哪些细节决定其效果。
- 对比、消融、可靠性或攻击实验分别支持什么结论。
- 贡献能应用于什么范围，还有哪些条件尚未验证。

优势必须有比较对象或设计依据。说明具体改进与证据，少用“显著提升”“领先”“开创性”等空泛判断。不要为了突出贡献，把采用的 ResNet、共形校准、联邦训练等已有方法写成新提出的算法。

避免在前面完整列一遍贡献，随后逐项重复同样的内容。标题、段落和图表各承担不同作用：标题帮助扫描，段落解释因果，图表呈现关键证据。研究意义应从实际问题与设计选择中读出来。

### 内容深度

| 类型 | 当前参考量级 | 要求 |
| --- | --- | --- |
| 常规工作 | 约 2,000–2,800 个汉字，按需要配图与表 | 讲清主线和代表性证据，避免流程细节淹没贡献 |
| 重点工作 | 约 4,000–5,000 个汉字，可更深入 | 增加设计机理、参数依据、实验设置、对比/消融、可靠性、攻击或部署证据及与既有工作的推进关系 |

以上是本次样稿的量级，不是每篇必须达到的配额。TIFS 是本次明确要求重点展开的工作；未来研究按用户指定的重要性与实际证据决定深度，不单凭期刊或会议名称分配篇幅。

与既有工作比较时，应说明研究问题和证据的推进。任务、数据和指标不同，不直接计算跨论文的“性能提升”；只有材料确认时才称某篇为另一篇的正式扩展版。

## 4. 沿用已确认的版式

页面结构：

1. 返回论文列表的入口。
2. 小字“研究介绍”。
3. 一个中文 H1 标题。
4. 标题下一行小字：会议/期刊与年份、论文 PDF、已确认的正式原文链接。
5. 导语和正文，按需插入原图与结果表。
6. 文末列完整英文题名、完整作者，再放原文和返回列表链接。

**不恢复导语后的大块论文信息卡片。** 会议和原文入口在标题下简洁呈现，英文题名与作者放文末，避免打断阅读。已经在标题下出现的会议信息，不在顶部小字中再次堆叠。

复用 `assets/css/research.css` 与现有主题，不为每篇建立独立设计系统。页面 front matter 保留 `lang: zh-CN`、`research_article: true` 和 `author_profile: true`。使用 `<article class="research-article" lang="zh-CN" markdown="1">` 作为内容容器。

### 图与表

- 优先使用与论点直接相关的论文原图。裁切保留子图标签、坐标、图例等必要信息，避免夹入相邻正文、页眉、稿件编号占位信息。
- 图注用中文解释图说明了什么，并标出原论文图号；图的观察条件和证据范围需要保留。
- 图片提供准确的 `alt`、实际宽高和 `loading="lazy"`。宽流程图或组合图用 `research-figure research-figure--wide`；普通图用 `research-figure`。
- 结果表通常控制在少量列内，写清指标、单位、协议与来源；手机端仍能阅读。无需完整复制论文所有大表。
- 图片只承担其实际证据作用；例如示意图不能代替实物实验，软件截图也不能独立证明延迟或安全性。

## 5. 先建立事实底稿，再写优势与意义

先读用户提供的全文及必要图表，记录研究对象、条件、已有局限、方法、贡献和证据。`ieee-paper-reader` 与 `humanizer-zh` 可用于技术梳理和中文表达，是否调用取决于当次任务及可用能力。

关键数字要能追溯到章节、图或表。至少核对以下区别：

| 容易混淆的内容 | 需要分开的口径 |
| --- | --- |
| 数据规模 | 实体标签/器件、身份类别、独立采集照片、增强图像 |
| 评估设置 | 已知类识别、开放集认证、未知输入拒识；主实验、压力测试、探索扫描、锁定测试 |
| 指标含义 | 相似度、识别准确率、攻击预测准确率、FPR、TPR、设备间极差 |
| 改善幅度 | 百分比与百分点；比较的是哪两个配置 |
| 安全证据 | 数字域伪造、实体重建、同工艺新样本、理论难度或成本分析 |
| 工程证据 | 仿真与实物测量、材料消耗与系统总成本、裸手机与外接成像附件 |
| 理论结论 | 假设、边际/条件/同时保证、估计组合空间与实际验证规模 |

摘要、正文、图表或界面有冲突时，记录不同口径，采用含义明确且可追溯的结果；必要时在公开稿限定表述，不能自行合并、挑选最有利数字或编造解释。尚未确认的出版信息与 DOI 不生成虚假链接。正式链接不可确认时，先保留已有的 PDF 入口。

论文中的限制应自然放在对应证据附近或文末，帮助读者判断适用范围。无需把介绍写成逐项审稿意见，也不能用流畅表达遮盖证据缺失。

四篇现有工作的详细底稿见 [RESEARCH_SOURCE_NOTES.md](RESEARCH_SOURCE_NOTES.md)。有新的证据或作者更正时，正文与底稿一起更新。

## 6. 文件组织与本地预览

| 文件/目录 | 用途 |
| --- | --- |
| `assets/pdf/` | 论文全文，目录名是复数 `assets` |
| `_pages/includes/pub.md` | 首页简介、发表信息、解读和 PDF 入口 |
| `_pages/research/<slug>.md` | 中文稿与固定 permalink |
| `images/research/<slug>/` | 该论文的图像资产 |
| `assets/css/research.css` | 解读页共用样式 |
| `_pages/includes/news.md` | 用户确认的新闻，和论文介绍分别维护 |
| `AGENTS.md`、README | 代理维护要求入口和面向维护者的项目说明 |
| `_docs/` | 持久维护规范、事实底稿与模板，不作为站点页面 |
| `_site/research-preview/` | 可重新生成的本地静态预览，不提交 |

选择简短、清楚的英文 slug，发布后保持链接稳定。内部链接和静态资源使用 Liquid `relative_url`；PDF 名含空格时正确编码。返回首页与解读入口使用 `target="_self"`，因为主题设有全局新窗口目标。

模板见 [templates/research-article.md](templates/research-article.md)。复制到 `_pages/research/` 后，替换全部占位内容，保持 front matter 与正文标题一致，并按实际图像填写宽高。不使用的示例图表和内部起稿注释应删除，章节按论文实际内容调整。只有已经确认的正式链接，才加在标题下的元信息中。

有 Ruby/Jekyll 时，优先使用真实站点构建与预览，命令见 [README](../README.md)。`run_server.sh` 使用相同的 `bundle exec jekyll serve` 命令，适用于兼容 shell。环境不支持时可生成与现有样式一致的静态预览，明确它不是完整 Jekyll 构建验证。静态预览应能从统一入口打开各篇文章，图片可嵌入，PDF 和返回入口在本地可用。当前 `_site/research-preview/index.html` 是已生成的本地文件，不是 Git 仓库自带的固定入口，新检出项目时应按需要重新生成。

不要把事实底稿只放在 `_site/`；该目录会被构建覆盖，也被 Git 忽略。`_docs/` 与 `AGENTS.md` 均在 `_config.yml` 的 `exclude` 中显式排除于站点输出，不加入 `include`。这与 Git 忽略无关：维护文档仍应纳入相应的版本管理。

论文列表标题调整的本地静态预览位于 `_site/publication-preview/index.html`；与研究解读预览一样，它是临时生成的核对产物，不提交，不替代完整 Jekyll 构建验证。

目录、模板、预览或发布方式有变化时，一并更新本规范、README 和必要的代理入口/模板注释。事实底稿只维护持久版本；旧的临时说明可保留指向它的链接，避免并行维护两份数据口径。

## 7. 推荐执行顺序与验收条件

1. 检查工作区、用户指定范围及已存在的材料；保留其他未提交修改。
2. 读取全文，确定这项工作的主要问题、贡献及数据口径，记录待核对项。
3. 写首页短简介与独立中文稿；重点工作按证据深入展开。
4. 提取并检查必要图片，补齐图注、表格和文末来源。
5. 接好首页入口，生成本地预览；核对数字、术语和贡献表述。
6. 检查 front matter、单一 H1、标题下元信息、文末出处、Markdown 列表缩进、图片尺寸及路径、内部链接和 PDF；排查占位符与未渲染的 Liquid/Markdown。
7. 用户要求发布后，执行下一节的提交与线上验证。

只为内容与可逆版式修改，不必建立镜像实现的单元测试。应完成有意义的结构、链接和渲染检查；未完成的验证要如实说明。

## 8. Git 与发布

默认先本地修改和预览。用户明确要求“git”“上传”“同步 GitHub”或发布时，视为授权提交并推送本次相关内容；无需重复确认。用户明确说“先不用 git”时，保留本地修改。

发布范围通常包含对应中文稿、`pub.md`、所需 PDF/图片及共用样式的必要改动。`news.md` 仅在任务涉及新闻或用户要求一并提交时纳入，保留用户确认的新闻内容。维护规范本身发生变化时，对应 `_docs/`、AGENTS、README 和必要配置也需要随该维护任务保存；其他已有个人配置、头像、字体或 README 修改，不能因为同在工作区就顺便提交。

README 区分了“只修改列表/新闻”和“新增或修改独立解读”两组提交示例；后一种不能仅暂存 `pub.md`，必须核对正文与资源的提交完整性。

提交前查看暂存文件列表和差异，执行 `git diff --cached --check`。不使用 `git add .`，不强推，不覆盖远程新提交。常规 Git 网络失败时，先定位连接问题；可用已认证的 GitHub Git 数据接口完成同一内容树的非强制发布，但须检查父提交、核对内容并保持本地/远程引用一致，不能输出凭据。

推送成功不等于站点已更新。验收应确认：

- 本次提交对应的 GitHub Pages 构建和部署成功。
- 首页实际包含新简介、解读入口，以及本次要求同步的新闻。
- 每篇页面的标题、正文结构、元信息和文末出处正确。
- 新图片、样式和 PDF 在线可访问；必要时用带提交版本的查询参数避开旧缓存。

最终向用户给出可直接打开的线上链接和简短提交标识，并说明任何实际未完成的验证。
